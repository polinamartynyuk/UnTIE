# Финальная архитектура метода: UnTIE H3 Consistency Gate

Статус: **FROZEN FINAL ARCHITECTURE**  
Дата фиксации: **2026-10-08**  
Версия спецификации: **1.0**  
Кодовое имя эксперимента: `H3-CONSISTENCY-GATE-3`  
Референсный прогон: `artifacts/qa_chunk_selection_h3_consistency_gate/run_20261008_01`

## 1. Зафиксированное решение

Финальной архитектурой проекта считается H3 с dataset-level consistency gate между H2 и H3. Gate выбирает один общий коэффициент `lambda` для датасета и разрешает отклонение от исходного H3 только при точном совпадении выбора на двух этапах обучения.

```text
TRAIN document-grouped OOF      -> lambda_train
TRAIN+VAL document-grouped OOF  -> lambda_refit

if lambda_train == lambda_refit:
    lambda_final = lambda_refit
else:
    lambda_final = 1.0  # исходный H3
```

Проверка доверительного интервала не входит в gate. Seeds не выбираются по качеству: всегда используются заранее заданные `42, 43, 44`.

## 2. Место архитектуры в pipeline

```text
документ
  -> детерминированные чанки
  -> dataset/language-specific B0
  -> frozen top-K кандидатов
  -> одинаковый QA reader для всех кандидатов данной cell
  -> признаки H2 и H3
  -> utility-модель + harm-модель для H2
  -> utility-модель + harm-модель для H3
  -> shared-lambda interpolation
  -> TRAIN/refit consistency gate
  -> utility/harm thresholds
  -> выбранный чанк либо fallback к B0
  -> ответ reader выбранного чанка
```

Общая концепция одинакова для русского и английского языков. Языково- и датасет-специфичными остаются уже зафиксированные B0, reader, вопросы, параметры чанкирования и обученные коэффициенты; логика H2/H3, обучение `lambda` и gate общие.

## 3. Компоненты H2 и H3

### H2

H2 является безопасным meta-reranker поверх B0. Для каждой альтернативы относительно B0 top-1 он использует:

- разность нормализованного B0 score;
- QA relevance и её взаимодействие с B0 margin;
- PairLEX, FullLEX и их взаимодействия;
- ранг кандидата, эффективный `K`, разрыв top-1/top-2 и энтропию B0;
- валидность ответов и признак двух пустых ответов;
- interaction-признаки QA relevance, лексического согласования и B0 margin.

H2 обучает две модели:

- Ridge для ожидаемого изменения Token F1 при переключении;
- logistic harm model для вероятности ухудшения.

### H3

H3 полностью сохраняет H2 и добавляет три agreement-признака:

- `delta_agreement`;
- `agreement_x_margin`;
- `fulllex_x_agreement`.

Таким образом, H3 не является отдельным несвязанным методом: это H2 с дополнительной группой reader-agreement.

## 4. Смешивание H2 и H3

Для каждого seed независимо обучаются H2- и H3-модели utility и harm. Их прогнозы смешиваются одинаковым для всех трёх seeds коэффициентом:

```text
utility = utility_H2 + lambda * (utility_H3 - utility_H2)
harm    = harm_H2    + lambda * (harm_H3    - harm_H2)
```

Зафиксированная сетка:

```text
lambda in {0.00, 0.25, 0.50, 0.75, 1.00}
```

Границы:

- `lambda=0` — H2;
- `lambda=1` — исходный H3;
- промежуточные значения ослабляют agreement-компонент, не меняя остальную архитектуру.

Один `lambda` выбирается по среднему document-grouped OOF Token F1 трёх seeds. При равенстве используются зафиксированные tie-break правила: меньше switch rate, затем большее `lambda`, то есть предпочтение исходному H3.

## 5. Обучение и защита от утечки

Для каждого датасета выполняются два независимых по роли выбора:

1. **Development selection:** document-grouped OOF только на TRAIN.
2. **Refit selection:** тот же алгоритм document-grouped OOF на TRAIN+VAL.

В каждом выборе:

- внутренние folds группируются по исходному документу;
- метрики трёх seeds усредняются, seeds не перебираются как гиперпараметр;
- `lambda`, регуляризация, harm-параметры и пороги выбираются без TEST;
- TEST не используется для выбора ветви, коэффициента или порогов.

Consistency gate сравнивает только два уже выбранных значения `lambda`. Если они различаются, неопределённость трактуется в пользу исходного H3.

## 6. Пороги и безопасное переключение

Для каждого seed пороги utility и harm обучаются внутри OOF. Кандидат может заменить B0, только если одновременно:

```text
predicted_utility >= tau_utility
predicted_harm    <= tau_harm
```

При отсутствии допустимой альтернативы сохраняется B0 top-1. Выбор порогов обязан удовлетворять зафиксированным evidence-ограничениям относительно B0:

- снижение Hit@1 не более `0.5` процентного пункта;
- рост HN@1 не более `1.0` процентного пункта.

Если допустимой пары порогов нет, policy переходит в `BASE_FALLBACK` и не переключает B0.

## 9. Статус seeds и воспроизводимости

Финальная научная оценка использует три фиксированных seed-specific policy и сначала усредняет их метрики внутри вопроса. Выбор «лучшего seed» запрещён. Текущий экспериментальный контракт не определяет дополнительный production-ensemble, превращающий три возможных ответа в один; это отдельная инженерная задача и не должно задним числом менять научную оценку.

## 10. Граница доказательности

Архитектура зафиксирована как финальное инженерное и исследовательское решение проекта. При этом consistency gate был сформулирован после анализа уже раскрытого official TEST. Его референсный результат имеет статус post-hoc evidence.

Поэтому допустимы два разных утверждения:

- **архитектурное:** финальный метод проекта — H3 Consistency Gate;
- **научное:** его преимущество над исходным H3 требует одной заранее зафиксированной проверки на новом закрытом split или независимом корпусе.

До такой проверки нельзя описывать `56.8603` как независимое подтверждение универсального преимущества. Исходный H3/P4 остаётся последней версией, полностью вошедшей в заранее определённый official-split benchmark, а consistency gate — финальной замороженной post-hoc архитектурой.

## 11. Политика дальнейших изменений

Любое изменение следующих элементов создаёт новую версию метода и не может молча называться этой финальной архитектурой:

- состава признаков H2/H3;
- сетки `lambda`;
- seeds;
- правила точного TRAIN/refit совпадения;
- fallback к `lambda=1`;
- utility/harm моделей и порогов;
- B0, reader, вопросной разметки или чанкирования конкретной cell;
- способа подсчёта основной метрики.

Новые гипотезы должны реализовываться отдельным экспериментом и записывать результаты в новый каталог.
